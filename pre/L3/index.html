上一版的问题是把四个产品都放进同一个“模型加工具”的框架里，结果看起来像四个颜色不同的卡片。今天我们换一个问法：每个产品认为 agent 最重要的东西是什么？是把 agent 变成个人基础设施，是让它从经验中积累程序，是把工作拆成可并行的工程任务，还是让它贴近代码现场的规则与权限？我们不做品牌排行榜，而是从工程机制反推设计哲学。

THE THESIS
Do not ask

Which product is smartest?

Ask instead

What does this product make persistent, parallel, or controllable?

THE SAME WORD HIDES DIFFERENT SYSTEMS

An agent product is

这一页是整课的 thesis。四个产品都可以调用工具、读写文件、运行任务，但它们把“工作”抽象成不同的对象。Hermes 把工作看成可积累的经验；OpenClaw 把工作看成跨渠道的个人基础设施；Codex 把工作看成可隔离、可并行、可审查的任务；Claude Code 把工作看成嵌入代码库和团队规则的现场实践。后面每一部分都只回答一个问题：这个哲学在工程细节里怎样实现？

Self-improvement here means controlled procedural accumulation. It is not silent weight training.

Hermes 的自进化是这次要展开的重点。官方文档把 memory 和 skills 分开：memory 保存关于用户、项目和偏好的事实；skills 保存遇到类似任务时可以复用的步骤。更关键的是，经验不会直接覆盖 live skill。它先变成 proposal，带有内容、证据、目标绑定、hash 和 rollback 信息，然后再经过 review 和 apply。这个设计哲学很像一个会写 runbook 的长期同事：它会积累，但积累必须能被检查、回滚和再次使用。

从工程角度看，Hermes 并没有把“成长”藏在一个神秘的模型状态里，而是把它拆到本地目录和工具协议里。memory、skills、cron、sessions 都是可以看见的对象。这样做的好处是长期连续性、跨 provider 和跨 surface；代价是状态治理变成了产品的一部分：旧 skill 什么时候 stale？谁可以 apply？不同 skill 是否冲突？所以 Hermes 的核心难题不是一次回答，而是如何维护一个会变大的 agent workspace。

Skill = procedural memory. It changes the agent’s method, not its weights.

Skill 这个词在不同产品里名字可能略有不同，但它解决的是一个共同问题：怎样把一次成功的工作方法复用到下一次。Skill 不是一个新模型，也不是单纯的一段提示词。它通常包含适用条件、步骤、应该调用的工具、例子和检查方法。它还可以采用 progressive disclosure，也就是先只显示名称和简介，真的遇到相关任务时才加载完整内容。要区分三个层次：memory 保存事实，skill 保存程序，model 保存更广泛的语言和推理能力。

Channel is an adapter, not the identity. OpenClaw makes routing, state, skills, and nodes the stable core.

OpenClaw 的不同不只是它支持很多聊天渠道，而是它把这些渠道当成 agent infrastructure 的入口。Gateway 负责把 WhatsApp、Telegram、Slack、iMessage 等 surface 接到同一个 agent core，再把 browser、nodes、skills 和 workspace 组织起来。这个设计的优点是 agent 可以“跟着人走”，不被某一个 app 绑死；风险是入口越多，身份、路由、session 隔离和权限越重要。它的工程哲学是：把 channel 做薄，把 gateway 做成稳定的 personal control plane。

OpenClaw 的 self-learning 进一步说明了“学习”和“自主”可以分开。它可以从对话、文件、URL 或纠正中提炼出 skill proposal，但 proposal 先停在 pending 状态，不会直接修改 active skill。官方设计还包括 scanner、hash 绑定、rollback metadata，以及 30 天 stale、90 天 archive 的生命周期治理。这个产品把 agent 当作个人基础设施，所以它必须同时处理“如何成长”和“如何不被一次错误经验永久污染”这两个问题。

A SHARED CONCEPT · MCP

MCP is a protocol
for connecting capability.

HOSTAgent applicationClaude Code · Hermes · another AI app
CLIENTMCP clientone session per server

Toolsmodel-callable actions
search · create · update

MCP standardizes the connection. It does not decide whether a tool should be trusted or allowed.

MCP 是 Model Context Protocol，重点不是创造一种新的 Agent，而是规定 Agent 应用怎样连接外部系统。官方架构里有 Host、Client 和 Server。Host 是 Claude Code、Hermes 或其他 AI 应用；Client 负责和某个 server 建立独立会话；Server 则提供专业能力。Server 可以暴露三类 primitive：Tools 是可以被模型调用的动作，Resources 是可以提供给模型的上下文和数据，Prompts 是面向用户的可复用模板。MCP 解决的是连接标准化，但它不自动解决权限、可信度和安全治理。

这三个概念很容易混在一起，但它们回答的是三个不同的问题。Skill 回答“应该怎样做”，它是方法和程序。MCP 回答“可以连接什么”，它是 Host 和外部 Server 之间的标准连接，里面可以有 tools、resources 和 prompts。Plugin 或 package 回答“怎样把一套能力分发出去”，它可以把 skill、app、配置和权限要求一起打包。比如做一个研究助手，literature review 的步骤可以是 skill，图书馆搜索和 Zotero 可以通过 MCP 接入，最后把它们和安装配置打成 plugin。理解这三层，才不会把一段提示词、一个 API 和一整套工作流混成同一个东西。

DESIGN PHILOSOPHY 03 · CODEX

Work becomes
parallel, isolated tasks.

mainstable repository
task Afix auth bugagent + sandbox
task Badd testsagent + sandbox
task Creview depsagent + sandbox
REVIEWdiffs · tests · merge
Codex turns autonomy into a queue of reviewable work packages. Parallelism is a product primitive, not just a model trick.

Codex 的核心设计哲学是 orchestration。官方介绍强调 worktrees、cloud environments、parallel agents、skills 和 background work。也就是说，它不只是在当前 terminal 里帮你补一段代码，而是把任务切成隔离的 work package：每个任务有 repo context、环境、执行过程和可审查结果，最后通过 diff、tests 和 review 回到主线。它把“agent 很能干”转译成“多个 agent 可以在不互相污染的情况下推进多个任务”。

Unit of improvement

An isolated run with evidence to review.

CODEX IS A WORKFLOW SYSTEM

The real output is not just code.
It is evidence.

INPUTTask + repoprompt, files, instructions, skill

如果只把 Codex 讲成“会写代码的 AI”，就会错过它最有意思的地方。它把 output 定义成一组 evidence：改了什么、在哪个 sandbox 里跑过什么命令、测试是否通过、最后应该 merge 还是 revise。它也把重复流程保存为 skill，让团队标准可以在多个任务中复用。Codex 的信任机制不是让 agent 永远不犯错，而是把每次 run 变成可以被人和系统检查的 review packet。

DESIGN PHILOSOPHY 04 · CLAUDE CODE

The agent lives inside
the codebase’s local rules.

MANAGED POLICYorganizationsecurity · compliance · shared policy
USER~/.claude/CLAUDE.mdpersonal defaults and preferences
PROJECT./CLAUDE.md · .claude/rules/architecture · commands · team conventions
LOCALCLAUDE.local.mdmachine-specific, personal project context
Context is hierarchical. The closer the rule is to the file being changed, the more local the instruction becomes.

Claude Code 的设计哲学更像“代码现场操作系统”。它不是把所有长期记忆都做成一个抽象的 memory，而是通过多层 CLAUDE.md 和 rules，把组织级、用户级、项目级和本地级规则加载到当前 codebase context。这样，agent 的行为不是只由 prompt 决定，而是由它正在工作的 repository 的制度环境共同决定。这里的 engineering choice 是 locality：让规则靠近它要约束的代码，同时保留从组织到项目的层级。

Claude Code 的不同在于它把 runtime lifecycle 暴露出来。CLAUDE.md 告诉 agent 应该知道什么；PreToolUse hooks 可以在工具调用前评估、拦截或要求确认；PostToolUse 可以在编辑后跑 formatter、lint 或 test；subagents 又可以把探索、计划和 review 分配给有不同权限的角色。这个设计哲学把“agent behavior”从一段 system prompt 扩展成 repository 中一套可以版本控制的过程控制。

现在把四个产品放在同一张机制表里。Hermes 持久化 facts 和 procedures；OpenClaw 持久化 personal state、channels 和 workspace；Codex 持久化 skills 以及可重复的 repo workflow；Claude Code 持久化 rules 和项目记忆。并行也不同：Hermes 是 subagent delegation，OpenClaw 是多 surface 和 node，Codex 是 worktree 和 cloud tasks，Claude Code 是 subagents、teams 和 lifecycle hooks。这样比较，我们就不再是在比较四个名字，而是在比较四种 state、concurrency 和 control 的设计。

THE SAME REQUEST REVEALS THE PHILOSOPHY

The verb “automate”
means four different things.

Hermeslearn the briefing procedurememory + skill + cron + delivery
OpenClawreach me wherever I amgateway + channel binding + workspace
Codexmake the artifact reviewablerepo + task run + diff + tests
Claude Coderespect the project’s rulesCLAUDE.md + hooks + permissions

这个例子可以让学生看到设计哲学如何改变同一个需求。Hermes 会把重点放在“以后每次都能按这个步骤做”，所以 memory、skill 和 cron 变得重要。OpenClaw 会把重点放在“我可以从哪个 channel 触发、结果送到哪里”。Codex 会把 briefing 看成一个 repo artifact，强调 diff 和 review。Claude Code 会先问这个项目的 CLAUDE.md、rules 和 hooks 对发布流程有什么约束。四者都能帮忙，但它们稳定下来的东西不同。

这一页避免一个常见混淆：产品宣传里的“会学习”通常不等于模型权重被重新训练。Hermes 和 OpenClaw 的 self-improvement 主要是把经验变成 memory 或 skill proposal；Codex 的改进可以沉淀成 reusable workflow；Claude Code 的改进可以写进 rules、skills 或 hooks。它们都在模型周围的 system layer 上做更新。这个层次更便宜、更局部、也更容易回滚，但它仍然需要治理，因为错误的规则同样会在未来反复执行。

DESIGN CHOICE
Start from the task

Not from the product’s popularity.

WHICH PHILOSOPHY FITS YOUR TASK?

Choose the center
of gravity you need.

What must stay stable?
Personal historyChoose a memory + skill runtime.→ Hermes
Many channels and devicesChoose a personal control plane.→ OpenClaw
Parallel engineering outputChoose isolated tasks and review packets.→ Codex
Repository rules and lifecycleChoose local context, hooks, and permissions.→ Claude Code

这不是一个产品推荐表，而是一个设计选择练习。先问任务中什么必须保持稳定。如果是个人历史、偏好和重复程序，Hermes 的 memory and skills 更贴合。如果是多个聊天入口和设备，OpenClaw 的 gateway 更贴合。如果是多个工程任务需要并行并最后审查，Codex 更贴合。如果最重要的是代码库规则、权限和开发生命周期，Claude Code 更贴合。真实项目当然可以组合这些机制，但组合前要先知道每个机制解决的是什么问题。

CLASSROOM LAB · 20 MINUTES

Reverse-engineer one product
from its mechanisms.

01StateWhat survives the turn?
02ImprovementHow does experience become reusable?
03ParallelismWhat can run at the same time?
04ControlWhere can a human stop it?
TEAM PROMPTChoose Hermes, OpenClaw, Codex, or Claude Code. Draw its persistence path, action boundary, and failure recovery path. Then name one design trade-off.
GOOD ANSWER“This product is optimized for X, because mechanism Y makes Z persistent—but that creates risk W.”

实验不要让学生再做一个泛泛的“agent architecture”图，而是要求他们反推一个具体产品。四个问题必须回答：什么状态能跨 turn 保留？经验如何变成下一次可复用的东西？什么可以并行？人在哪里能停止或审查？最后必须写出一个 trade-off。例如，Hermes 的持续积累带来个性化，也带来 stale skill；Codex 的并行带来吞吐，也带来 merge 和 review 成本；OpenClaw 的多渠道带来可达性，也带来路由和身份风险；Claude Code 的本地规则带来贴合项目，也带来上下文层级复杂度。

最后回到一句话：不同 agent 让不同的东西稳定下来。Hermes 让经验稳定下来，OpenClaw 让个人基础设施稳定下来，Codex 让并行工程吞吐和 review 稳定下来，Claude Code 让代码库里的规则和生命周期稳定下来。理解这一点，学生就不容易被“谁更强”带走，而会开始问一个更工程化的问题：我希望什么东西在下一次任务里继续存在？
