Lesson 01 gave us a map of the AI stack. This lesson zooms in on the word learning. We will keep the classical ideas—representation, objective, optimization, and generalization—but connect them to the systems engineers actually build today. The key shift is simple: a strong model is not automatically a strong learning system.

Core question

What changes when learning moves from a classroom dataset into a living product?

THE THROUGH-LINE

The model is only one part of learning.

Classical textbook

Fit parameters to a fixed dataset, then estimate performance on held-out examples.

data → model → score

2026 engineering

Compose data, pretrained weights, adapters, retrieval, evaluators, serving, and feedback.

system → evidence → update
Learning objective. Explain why a reliable AI system requires more than a low training loss.

Students often learn machine learning as a neat pipeline. That pipeline is a useful first approximation, but it becomes misleading when we build foundation-model applications. Today we will repeatedly compare the classroom version with the engineering version. The goal is not to reject the textbook. It is to understand where the textbook stops.

ONE COMPARISON TO KEEP

A model learns.
A system keeps learning.

TEXTBOOKFixed dataset

One target · one loss · one test set

→
FRONTIER PRACTICELiving system

Data · model · evals · traces · updates

This is the contrast to return to throughout the lesson. In a textbook, the data and test set appear stable. In production, the world changes, users adapt, and the system may include retrieval, tools, and human review. So the engineering question is not only “How good is the model?” It is also “How do we know what changed, what failed, and what to update next?”

01

PART ONE

What does it mean
to learn?

The word “learning” is larger than changing weights.

We start by widening the definition of learning. A model can learn during pretraining or adaptation, but a useful AI product may also improve through better context, retrieval, tools, evaluation, and feedback. The first part gives us the broader frame.

PART 01
Question

Where can improvement happen?

Classical answer

Inside the parameters.

LEARNING LOCATIONS

Improvement can happen in four places.

01Base modelPretraining changes the general representation.
02Adapter or post-trainingTask-specific behavior is added with a smaller update.
03Context and toolsRetrieval and tool results change what the model can answer now.
04Feedback loopFailures become tests, data, and release decisions.

Ask the class to locate “learning” in each example. If a model receives a new document through retrieval, its weights did not change, but its behavior may improve. If an adapter is trained, the base model may remain frozen while the system becomes better at a task. The useful definition is therefore behavioral and operational, not only parametric.

A MORE USEFUL EQUATION

Reliable behavior =
model × context × feedback

MModelWhat the learned weights can do
CContextWhat the system makes available
FFeedbackWhat the system can notice and improve

This is not a mathematical identity. It is a teaching shorthand. A capable model can still fail when it receives the wrong context or has no way to detect failure. Conversely, a smaller model can become useful when the task is well-scoped, the relevant evidence is retrieved, and the system has good evaluation and review loops.

02

PART TWO

The learning problem
is a design problem.

Before model selection comes task specification.

The textbook often gives us a clean target variable. Real projects rarely do. We need to decide what the system can observe, what success means, what happens under uncertainty, and which errors matter most. This is where technical work meets organizational purpose.

PART 02
Specify before training
  • Observation
  • Outcome
  • Constraints
  • Uncertainty
  • Escalation

TASK SPECIFICATION

Turn a vague goal into a testable contract.

OBSERVEWhat may the system see?
PRODUCEWhat must it return?
PROTECTWhat must it never do?
ESCALATEWhen should a human decide?
Textbook: “Predict the label.” Engineering: “Support this decision under these evidence, risk, and response constraints.”

Have students rewrite a vague request such as “build an AI assistant” into four boxes. The important move is to make the system contract visible. The target is not merely an answer; it includes evidence, format, refusal behavior, and what happens when confidence is low.

03

PART THREE

Representation is
the first bottleneck.

The optimizer cannot recover information the representation discards.

Classical machine learning foregrounded feature engineering. Modern models foreground learned representations. The central idea remains: what the system sees determines what it can learn. Embeddings make this concrete because they turn many forms of data into a space where similarity and distance become operational.

An autoencoder is a useful bridge between feature engineering and learned representation. The encoder maps the input into a smaller code, and the decoder tries to reconstruct the original. The model is not told which features to preserve directly. The reconstruction objective creates pressure to preserve information that helps rebuild the input. The bottleneck is where the representation becomes visible.

VAE · PROBABILISTIC LATENT SPACE

A VAE learns where to sample.

The VAE adds probability to the autoencoder. Instead of assigning every input one exact latent vector, the encoder predicts a distribution. Sampling makes the latent space continuous and generative. The KL term keeps that distribution close to a prior, usually a standard normal. The visible trade-off is important: more regularization can improve smoothness and interpolation while making exact reconstruction harder.

Terminology check

Remember

ReLU and tanh are not losses.

DO NOT MIX THESE ROLES

ReLU and tanh transform signals.
Loss functions score outcomes.

COMPONENTJOBEXAMPLES
Activationnonlinear transform inside the networkReLU · tanh · sigmoid · GELU
Losscompare output with target or preferenceMSE · cross-entropy · KL
Regularizeradd a preference or constraintweight decay · sparsity · VAE KL
ReLUmax(0, x)
tanhbounded in [-1, 1]

This is a terminology correction worth making explicit. ReLU and tanh are activation functions, not losses. They sit inside the network and shape the signals passed from one layer to the next. A loss function sits at the training objective and scores the output against a target or preference. A regularizer adds another preference or constraint. Keeping these roles separate prevents a lot of later confusion.

Important: an AE does not “understand” anomalies automatically. The threshold and training distribution define what counts as unusual.

Autoencoders are not only a textbook compression trick. A denoising autoencoder learns to remove a corruption process. An anomaly detector can use reconstruction error as a signal, but only relative to the normal data used in training. If the training set contains the anomaly, the model may learn to reconstruct it too. The engineering question is always: unusual compared with which reference distribution?

Here the latent space is the star of the visual. A plain autoencoder may scatter examples in a way that reconstructs well but leaves gaps. The picture is conceptual, not a claim that every real VAE produces two tidy clusters.

What changes: the decoder is fixed; the sampled latent code changes. What stays: the learned structure of the decoder.

This is the generative intuition. Once the VAE has learned a structured latent space, we can sample a point and ask the decoder to produce an output. Nearby samples should often produce related outputs, although the quality depends on the dataset, architecture, and objective balance. This is also a useful place to explain that generation is not retrieval: the decoder synthesizes from learned parameters rather than copying one stored example.

This map prevents AE and VAE from becoming isolated vocabulary. Every architecture introduces a preference about the patterns it can represent efficiently. CNNs make local spatial patterns easy. Transformers make long-range relationships easy. Diffusion models turn generation into a sequence of denoising steps. The lesson is not to memorize a leaderboard; it is to connect architecture, inductive bias, and objective.

04

PART FOUR

Inductive bias:
what does the system assume?

Generalization is impossible without structure.

Inductive bias is one of the most important ideas that beginners often memorize without feeling. Every learner must prefer some hypotheses over others. In modern AI the bias is distributed across architecture, data mixture, post-training, retrieval, tools, and policy. The model is not assumption-free; the assumptions are simply harder to see.

PART 04
Bias stack
  • Architecture
  • Data mixture
  • Post-training
  • Context
  • Policy

THE BIAS STACK

Modern systems distribute assumptions across layers.

policy & escalation
retrieval & tools
instruction & preference
pretraining data
architecture
Question: Does the system’s full set of assumptions match the world where it will operate?

In a small textbook model, we can often name the prior: linearity, locality, smoothness, or sparsity. In a foundation-model application, assumptions are layered. The data mixture shapes the base model; instruction tuning shapes behavior; retrieval shapes the evidence available; policy shapes what can be done. The system’s inductive bias is the stack.

05

PART FIVE

Loss functions
encode priorities.

The system optimizes the signals it can see.

A loss function is not just a technical object. It turns a priority into a direction for optimization. In open-ended AI, we usually need several signals: helpfulness, groundedness, safety, cost, and latency. What is absent from the objective will tend to be absent from the optimization pressure.

PART 05
Objective design

One scalar rarely captures the whole task.

Modern move

Use multiple evaluators and release gates.

MULTI-OBJECTIVE SYSTEM

What counts as “better”?

Modern adaptation: LoRA / QLoRA updates a small trainable adapter while keeping a large base model mostly frozen.

Use the dials to explain why “accuracy” is not enough for a deployed AI system. A response can be correct but too slow, too expensive, unsafe, or impossible to audit. The modern practice is not to pretend these trade-offs disappear; it is to make them explicit and evaluate them together.

06

PART SIX

Optimization is
not understanding.

A system can optimize perfectly toward the wrong target.

Gradient descent is one of the cleanest stories in machine learning: compute error, follow the gradient, repeat. At scale, the optimization problem also becomes a systems problem involving memory, parallelism, precision, checkpointing, and serving. But none of this changes the central warning: optimization only follows the objective we supplied.

PART 06
Diagnostic view

Training loss is evidence, not a verdict.

Watch for

divergence · oscillation · overfit

TRAINING DIAGNOSTICS

Two curves can tell two stories.

Visual idea adapted from Google ML Crash Course.

Point to the moment where the validation curve turns upward. The model is still getting better at the training objective, but its behavior on the validation set is getting worse. This is the basic picture of overfitting. In production we extend the same logic: a change that improves one metric can degrade another, so we need multiple curves and release checks.

Keep the classical optimizer on the board, but widen the picture. At modern scale, the engineering team must make the run fit into memory, survive failures, produce comparable checkpoints, and serve the result under cost and latency constraints. Training and serving are connected by the same quality and resource trade-offs.

07

PART SEVEN

Generalization
under new conditions.

Unseen data is not one kind of novelty.

The textbook test split usually assumes that unseen examples come from the same distribution as training examples. That is a useful statistical baseline, but deployed AI encounters time, geography, language, policy, interface, and adversarial shifts. We need to teach students to distinguish a random holdout from the real deployment distribution.

Engineering move: split by time, source, user, geography, task family, and failure condition—not only at random.

Ask which of these distributions a random test split represents. Usually it approximates the second box. It says little about the third and fourth boxes. This is why modern evaluation uses temporal holdouts, challenge sets, red-team cases, and shadow deployments. The point is not to eliminate uncertainty; it is to expose the uncertainty we need to manage.

08

PART EIGHT

Spurious correlations
and data failure.

The model can be right for the wrong reason.

We often tell students that overfitting is a model problem. Modern data work teaches a harder lesson: the failure may be in the dataset. Leakage, duplicates, source identifiers, and artifacts can make a model appear strong while it learns a shortcut that disappears in deployment. Data composition is a modeling decision.

PART 08

This is why counterfactual pairs and slice analysis are so useful: they ask whether the answer survives when a tempting shortcut is removed.

09

PART NINE

Evaluation is
measurement design.

A benchmark makes some failures visible—and leaves others invisible.

Evaluation is often taught as the final score. Modern AI engineering treats it as a development instrument. We need a suite of cases and scorers that makes the important failures visible. For open-ended systems, that may combine exact metrics, rubrics, human review, model-based judges, trace checks, safety tests, and operational metrics.

PART 09
Scorecard

No single metric can carry the whole task.

Release gate

Improve the target without creating unacceptable regressions.

EVALUATION SUITE

Measure the output and the system around it.

Have students compare the scorecard with accuracy. Accuracy may answer only the first row, and only for a narrow task. The other rows are not optional extras when the system is used in the world. A release should improve the target behavior without hiding regressions in grounding, safety, or operational reliability.

It also gives us richer material for evaluation datasets: real failure cases, intermediate decisions, and the context that produced the result.

PART TEN

From model
to learning system.

Deploying is the beginning of the feedback loop.

The final part puts the pieces together. A production learning system is versioned, evaluated, observable, and governable. When performance changes, we need to diagnose whether the cause is data shift, retrieval, prompt, tool policy, model, serving, or user behavior before deciding what to update.

A PORTABLE CHECKLIST

Interrogate any ML system with five questions.

01What does it see?representation + context
02What does it assume?inductive bias
03What does it optimize?loss + priorities

These five questions are the portable takeaway. Students can use them to analyze a classifier, a recommendation system, a language model, or an agent. The questions prevent the conversation from collapsing into model-brand comparison. They force us to inspect the assumptions and feedback loops around the model.

CHECK
One-minute test

Choose the stronger explanation.

Answer

B is stronger because it names the system surface.

CHECK YOUR UNDERSTANDING

Why can a lower loss fail to improve the product?

A
Because optimization never changes the model.

Not quite. Optimization can change the model while still missing the product objective.

B
Because the objective, data, or evaluation may not represent the real task.

✓ Correct. A system can improve its measured signal while becoming less useful in context.

C
Because test sets are never useful.

Test sets remain useful; they simply answer a limited question.

This check is designed to separate skepticism from rigor. We are not saying that losses, metrics, or test sets are useless. We are saying they are instruments with a scope. The engineering task is to make the scope visible and add the evidence needed for the decision at hand.
